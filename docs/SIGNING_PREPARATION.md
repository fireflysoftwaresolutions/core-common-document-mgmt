# Signing preparation contract

This is an internal, explicitly composed preparation workflow. It exposes no new HTTP route and installs no authentication, authorization, resource-binding, storage, or provider adapter. Missing current authority or a trusted typed resource-tenant binding refuses preparation. A platform tenant or opaque subject is never parsed into a resource UUID or `createdBy` identity.

`SigningDraftIntent` accepts the bounded single-signer BASIC/PDF_VISIBLE subset, explicit existing signature/document/version/provider identifiers, supported placement and settings. Unsupported metadata, signer settings, or provider refuses before I/O. An existing server-registered account binding supplies the exact provider, account, HTTPS endpoint, and immutable binding version. The genuine envelope adapter's read-only account lookup must match it; lookup does not grant authority or create a client.

The authority adapter consumes genuine `SecurityContextPort`, `PolicyDecisionPort`, and Kernel `AuditActor` types. It preserves opaque issuer/subject/client/platform-tenant values. It requires a live JWT expiry, an already-issued typed resource binding for the exact resource tenant, actual PERMIT, and no unfulfilled obligations. This milestone supports no obligation executor. Application wiring must supply a trusted `SigningTenantBindingResolver`; there is no fallback resolver or HTTP-security installation claim.

## Durable local state

An operator may review and install `core-common-document-mgmt-models/src/main/resources/db/optional/document-signing/V6__Signing_Preparation.sql` and then `V7__Signing_Original_Audit.sql` explicitly, after the exact reviewed PostgreSQL17 canonical immutable-audit deployment. They are outside automatic migrations. It adds four mapped tables under `document_signing`: `account_binding`, `envelope`, `operation`, and `request_binding`. It adds scoped unique indexes to existing metadata tables and scoped foreign keys for tenant, document/version, signature/provider, account binding/version, and local associations. Existing V2 and its global request-reference uniqueness remain unchanged. No row is backfilled or adopted and no provider identifier is inferred. Manual installer delegation and its narrowly enumerated owner/runtime ACL are described below; application startup executes no installer, creates no role and grants no privilege.

The first short Spring Data transaction locks the exact account/provider/document/version/signature metadata, records the source fingerprint, canonical intent and finite authority evidence, and inserts independent local envelope/request/operation UUIDs. The operation starts `PREPARING`, generation zero, with no captured content. The request has a planned signer slot, no confirmed recipient, and no legacy request association.

The transaction publisher completes before content I/O starts. `DocumentContentPort.getContent` is called once using the explicit selected **version** UUID. Captured bytes are copied, bounded to 10 MiB, required to be PDF, and bound to their exact SHA-256, byte length, filename and media type. They are candidate bytes for a future approval, not a claim that a legacy version digest or historical approval already exists. The immutable intent and content use redacted generic JSON/toString representations; the explicit canonical-intent method is for authorized storage and must not be logged.

After I/O, the workflow rereads the adapter account binding and current principal, resource binding and policy. The authority window is clipped to the original deadline and can shorten; it cannot renew. A second short transaction rereads the locked metadata and checks the complete source fingerprint. Mapped Spring Data Criteria/Update compare-and-set fences include tenant, account-binding version, state and operation generation. Exactly one row must match. Content length/SHA checks and immutable identity/intent/content triggers provide defensive database constraints. Preparation returns only after the transaction publisher completes. Captured content cannot be replaced or a prepared operation reopened.

Storage never runs under an ambient reactive transaction. The transaction boundary rejects participating/non-new transactions; controlled genuine Spring transaction tests prove that row `onNext` does not escape before commit completion. They do not prove physical database connection release, actual database constraints, isolation, or a physical commit deadline. Those require a separately authorized native gate. Reactive deadline cancellation cannot claim that an already-started physical commit was undone.

Expiry or refusal leaves an incomplete operation observable where the first phase committed. This milestone has no renewal, cleanup mutation, or technical reconciliation grant to relabel it successful. A future governed reconciler is a separate contract.

## Paired canonical audit source implementation

The new source uses the existing genuine `TransactionalAuditAppender`, Kernel canonical audit values, `OwnedLeaseConnectionFactory`, `BoundedR2dbcResources`, and `DefaultBoundedRootTransaction`; it does not create a second journal or hash-chain implementation. The public store constructor creates all eight real Spring Data repositories from the same verified client/template/manager/factory graph as the genuine appender. The earlier generic-transaction compatibility constructor refuses all new business writes before metadata reads. Missing append authority or signing audit admission cannot select a fallback implementation.

A required `SigningAuditAdmission` must independently verify the existing typed resource binding and supply its actual resource-tenant UUID plus current policy revision and process/correlation IDs. It must not parse or invent these from the legacy tenant string or opaque subject. There is no default implementation. The appender additionally requires the existing genuine `AuditAppendAuthority` contract; an event or permit record is not a grant.

Both reservation and prepared-state phases append their exact new event before mapped business writes within the same bounded owner root. Exact canonical record hash/event equality and non-replay are required. Event metadata contains only typed IDs, opaque authenticated actor/provenance, policy revision and evidence digest. Evidence binds the operation/envelope/account-binding version, signature/document/version/provider, immutable intent/source/original-authority-provenance digests, and the captured content digest for the prepared phase. No PDF, signer intent text, mutable DTO, or provider payload enters the audit record. `COMPLETED` describes the local reserve/prepare phase; it never means sent or signed.

The prepared event causes from the reservation event and retains its exact operation stream, actor, policy revision and process/correlation. Before a completion append or update, a mapped query loads the exact persisted request by request/operation/envelope/tenant and validates its complete provider/account-version/signature/document/version/planned-slot tuple and absent legacy/external association. Missing, foreign, or conflicting rows refuse. Request rows cannot update or delete under the optional guards, so this read needs no added row lock or UPDATE grant. The result uses that persisted request ID. Mapped CAS predicates also require the reservation event and audit scope. Each phase intersects current admission with the original finite authority and a five-second technical owner cap; this grants no new time. The result is withheld until the actual owner completion reports commit acknowledgement, completed boundary, and complete cleanup. Appender/business failures request rollback of the active root. Controlled genuine Spring/owner-root tests over a networkless SPI lease exercise rollback calls and withholding; they are not proof of physical database rollback/commit or durable event rows.

A later phase refusal can leave the **earlier committed, audited PREPARING reservation**. The whole journey must not be called rolled back. No persisted failure state is written in this milestone. A future persisted failure or reconciler must itself append its paired event under independently valid authority; this code neither renews authority nor relabels incomplete state successful.

## Explicit manual owner installation boundary

V6 requires separately provisioned restricted `document_signing_guard` and canonical `firefly_audit_writer` roles and an installer delegated SET to the signing owner plus existing metadata-index/REFERENCES authority. V7 additionally requires explicit SET delegation to `firefly_audit_guard`. The scripts create no roles, adopt no unknown owner, and refuse incompatible role flags/memberships. The four tables are owned by the non-login signing guard. V6 installs no usable runtime business-table privileges before the bridge exists.

The narrow V7 `firefly_audit.document_signing_require_audit` function is owned by the existing audit guard, `SECURITY DEFINER` with only `pg_catalog` in search_path, and executable only by the signing guard. It verifies exact full current transaction ID, backend/session, operation/event stream, completed-new canonical context, safe metadata and digest. Every loaded selected/reservation row and the current prepared row is checked by the exact installed `firefly_audit_private.require_record_hash(firefly_audit.audit_event)` before metadata acceptance; Java checks do not substitute for this SQL boundary. Installation requires that helper and its canonical-text/record-bytes dependencies with their exact signatures, result types, audit-guard owner, immutable invoker mode, fixed search_path and owner-only ACL. No runtime helper grant is added. Prepared verification additionally checks immutable reservation causation. Ordinary runtime audit reads close after append completion; the bridge follows the existing owner-only document-generation V5 pattern and returns no audit payload. It grants runtime users no audit SELECT, audit-guard/signing-guard membership or broad audit capability. Temporary REFERENCES privileges are revoked after scoped event FKs are installed, and exact function ownership/definer/search_path/signature/ACL are checked.

Defensive schema constraints bind both event references to canonical immutable audit rows, recompute the documented ASCII `CORE_SIGNING_EFFECT_V2` phase-evidence digest from typed IDs and stored digests, and refuse mismatched actors/process/policy. Deferred graph guards prevent partial envelope/operation/request state from committing. Captured bytes/intent/identity remain immutable, operation/envelope transitions occur only once, and deletion is unavailable. The public metadata read/row-lock permissions are **separate, already-governed prerequisites**; V7 checks them and never grants them. The new account-binding table grants only SELECT and UPDATE(version) needed by PostgreSQL row locking; its owner trigger refuses every runtime UPDATE. Account registration/revocation is an administrative authority lifecycle, not implemented or claimed audited by this preparation workflow, and no seed data is installed.

All installer controls are source review/static-shape evidence until a separately authorized native gate validates exact SQL, role ACL, RLS coupling, FK/trigger behavior, canonical event bodies, isolation, rollback, and physical cleanup. Immutable snapshot guards and ordinary logs are not audit adoption. This source does not claim legal custody, WORM protection, all-owner adoption, provider acceptance, or a physically bounded commit. The mandatory trusted authority/admission composition also remains deliberately unwired.

## Dispatch remains closed

`SigningDraftWorkflow.dispatch` is unsupported. No envelope create/send/void, notification, reminder, legal cancellation, or cryptographic verification is performed. A future dispatch must bind actual approval and current authority to the stored exact intent/version/content digest and adopted account-scoped provider association, using a separately qualified immutable-content provider capability. A document-ID refetch is not an acceptable substitute.

The old local-success paths are intentionally removed: `initiateSigningProcess`, `cancelSignature`, `sendNotification`, and `sendReminder` return `SigningIntegrationUnavailableException` before business repository/provider interaction. The actual existing notification/reminder HTTP operations declare 503; the shared error handler produces the error response. There are no new initiation/cancellation HTTP-route claims. Existing HTTP/DTO and public service signatures remain. Previously recorded positive provider-path tests remain historical and are not acceptance for this preparation-only workflow.

The checked-in canonical SDK OpenAPI resources and generated SDK are byte-preserved and **stale for the new 503 behavior**. Regeneration must use the genuine running producer after the framework dependency/source gates; no specification or SDK is hand-edited here. Source tests, later producer generation, native database acceptance, provider acceptance and legal-business adoption are separate gates.


## Explicit original-policy custody path (V3 source)

`SigningPreparationRuntimeFactory.createPolicyCustody` is a separate opt-in composition. Old factory implementations default to refusal; existing `create` and store constructors retain V2 behavior and do not install or select V3. The concrete factory passes its same private `TrustedSigningRuntime` as phase admission, trace provider and append authority. Missing V3 capability refuses before lease or business I/O. No new HTTP endpoint, bean/default activation, account registration or provider dispatch is introduced.

For each committed phase, `SigningAuditedPhase.executeV3` reads the exact trace from the entered private phase, binds the unchanged business evidence to its V3 commitment and appends a new canonical event. It rejects replay as authorization for new effects. A generated Spring Data INSERT then writes one `policy_custody` row and a derived repository rereads the exact tenant/resource-tenant/operation/event/phase tuple. Full row equality and exactly one affected insert precede business writes and CAS in that same owner root. Any failure requests rollback of that root. The independent row UUID is local identity; engine decision IDs and event IDs are not assumed globally unique. The row retains the ordered original authorization/admission revisions and opaque decision IDs, V2 business digest and trace digest. Generic JSON and toString redact these values.

`SigningOperationPolicy` is an additive mapped projection for protocol and reserve/prepared trace commitments. The original `SigningOperation` record, its 30 components and both constructors are unchanged. Generated operation INSERT merges mapped outbound columns with equality checks on overlapping fields. Completion validates the persisted reservation custody against its original canonical audit commitment and adds protocol/reservation-trace/prepared-trace-null predicates to the existing full business/state/generation CAS. A legacy row cannot be silently resumed as V3. A new replay admission does not rewrite or become proof of the original decisions. Prepared evidence keeps the original stream/actor/process/correlation/policy-revision constraints; a revision change between phases refuses rather than expanding the old contract.

A separately delegated operator must review optional `V9__Signing_Policy_Custody.sql` after exact V6/V7 and canonical audit installation. It changes no old SQL file or historical row. Nullable operation columns preserve old rows, while new guarded operations require explicit protocol 3. Scoped deferred FKs and both directions of the operation/custody graph prevent stray or partial custody from committing. Guard-owned code recomputes the unchanged V2 digest, strict length-framed UTF-8 trace and V3 commitment from actual stored rows, then invokes the existing canonical current/predecessor audit bridge. Dedicated opaque-ID validation preserves Java UTF-16 bounds and Unicode whitespace/control semantics without trimming or normalization. The installer checks prior function bodies, owners, signatures, search paths and ACLs; temporary event REFERENCES are revoked. Runtime gains only required SELECT/INSERT on the new table and UPDATE of the prepared trace column, without audit SELECT, private helper execution or role membership.

The existing V6/V7 signing tables have no tenant RLS policy, and V9 does not introduce a tenant-confidentiality claim. Scoped queries/FKs are not database-wide read isolation. All V9 SQL/ACL/trigger behavior, physical transaction durability and cleanup remain pending a separately authorized native gate. Controlled genuine SDK/OAuth/PDP, Spring Data and owner-root source tests are not physical database or provider acceptance. If the first audited PREPARING phase committed and a later phase refuses, that reservation remains an observable incomplete operation; it must not be reported as a fully rolled-back journey. No new failure state, reconciliation grant or authority renewal is added.

V3 does not relabel an inside-root error from a private legacy exception marker. It retains the opaque bounded-root failure after rollback/cleanup. The old V2 path remains compatible; no unqualified shared rejection-key service adoption or HTTP classification is added. A fresh check of the original authority and scope immediately after custody readback prevents the business callback from running if that read consumed the remaining window.
